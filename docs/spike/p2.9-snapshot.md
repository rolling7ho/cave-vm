# P2.9: snapshot experiment

A running guest is paused at its shell prompt, saved to a directory, and
restored in a new process. There the shell keeps running: it takes typed
commands, `sleep` works (so the timer does), uptime carries on from the
snapshot, and `poweroff -f` ends the VM cleanly.

**Answers:** A1 holds. The GICv3 state from `hv_gic_state_get_data` plus the
per-vCPU `ICC_*` registers restores in a new process. A2 holds. The general,
SIMD and EL1/EL0 system registers, plus the virtual timer offset and mask,
are enough for an exact restore of this guest.

## Machine

Apple M4 Pro, 24 GiB, macOS 27.0.1 (26A434). Every Hypervisor.framework call
used is available on macOS 26 (the `hv_gic_*` calls since macOS 15). Guest:
the P2.7 kernel and initramfs, 1 vCPU, 512 MiB.

## What a snapshot holds

| Part | Source | Size |
|---|---|---|
| General registers x0 to x30, PC, CPSR, FPCR, FPSR | `hv_vcpu_get_reg` | 35 values |
| SIMD and FP registers q0 to q31 | `hv_vcpu_get_simd_fp_reg` | 512 bytes |
| EL1/EL0 system registers, including `CNTV_CTL`/`CNTV_CVAL` | `GUEST_STATE_SYS_REGS` | 37 values |
| GIC CPU interface registers | `GUEST_STATE_ICC_REGS` | 9 values |
| Guest virtual counter at pause, and the timer mask | offset and mask calls | 2 values |
| GIC distributor and redistributor | `hv_gic_state_get_data` | 126,314 bytes |
| PL011 registers and unread input | the device model | under 100 bytes |
| Guest RAM | `memory`, a sparse file | 512 MiB logical, 25 MiB on disk |

The guest's virtual counter is saved instead of the raw offset. Restore sets
`offset = host now - saved counter`, so guest time continues from the pause
and does not jump by the time the snapshot sat on disk.

Restore order: create the GIC, map `memory` copy-on-write (`MAP_PRIVATE`),
create the vCPU, set `MPIDR_EL1`, write the GIC state (it finds
redistributors by MPIDR), then the vCPU registers, the timer offset and the
UART.

## Steps

```sh
image/spike/build.sh
cargo build --release -p cave-vm-vmm --bin cave-vmm-spike
scripts/hypervisor-runner.sh target/release/cave-vmm-spike \
  --kernel target/spike/Image --initrd target/spike/initramfs.cpio.gz \
  --stop-at "~ # " --snapshot /tmp/snap </dev/null
scripts/hypervisor-runner.sh target/release/cave-vmm-spike --restore /tmp/snap
# at the restored prompt:
echo restored-ok; uname -r; cat /proc/uptime; sleep 1; poweroff -f
```

## Numbers

20 restores, each piping `echo RE''ADY` into the restored shell and stopping
when `READY` is printed. The binary was already signed.

| Measure | Result |
|---|---|
| Save: capture vCPU, GIC and UART state | 2.5 ms |
| Save: write the sparse memory file (scans all 512 MiB) | 156 ms |
| Restore: VM, GIC, memory mapping, vCPU and state ready | median 2.9 ms (2.7 to 3.2) |
| Restore to the first command's output, in process | median 4.4 ms (4.0 to 4.7) |
| Restore to the first command's output, wall clock with exec | median 6.7 ms (6.2 to 7.7) |
| Resident memory of a restored VM after one command | 12 MB |

Restore is fast because nothing is copied. The memory file is mapped
copy-on-write, and only the pages the guest touches are faulted in. Save time
is dominated by reading every page to find the zero ones. Phase 4 can cut
that by tracking dirty pages or by keeping RAM in a file from the start.

## Limits of this experiment

- Same machine and macOS build for save and restore. Whether a GIC state blob
  loads on another macOS release is not known. The design's fallback for a
  memory snapshot that cannot be loaded (boot from disk) covers it.
- One vCPU. Phase 3 added 2-vCPU snapshots (decision 0005, addendum).
- The guest was only tested right after restore. Once it went idle it hung,
  because the GIC blob leaves out each redistributor's SGI and PPI state.
  Phase 3 fixed this by saving those registers too (decision 0005,
  addendum).
- The vCPU is paused between exits by `hv_vcpus_exit`, so no MMIO access is
  half done. Phase 4 should keep that rule.
- The `state` format is versioned but is a spike format. Phase 4 defines the
  stable one.
