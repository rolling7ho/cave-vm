# P2.7: spike kernel boot

The spike kernel and initramfs from `image/spike/` boot to a busybox shell on
the PL011 console under `cave-vmm-spike` (P2.6). Typed commands run and
`poweroff -f` ends the VM with PSCI `SYSTEM_OFF`.

## Machine

- Apple M4 Pro, 24 GiB, macOS 27.0.1 (26A434).
- The code only calls Hypervisor.framework APIs available on macOS 26.
- Guest: 1 vCPU, 512 MiB, Linux 6.18.56 (`allnoconfig` plus
  `image/spike/kernel.config`), busybox 1.37 initramfs.

## Build

```sh
image/spike/build.sh            # Apple container; writes target/spike/
```

Output: `Image` 4.7 MiB, `initramfs.cpio.gz` 1.0 MiB.

## Boot time

Measured from process start to the guest printing `cave-spike: shell ready`
(printed by `/init` just before the shell starts), with a release build that
was already signed:

```sh
cargo build --release -p cave-vm-vmm --bin cave-vmm-spike
codesign -s - -f --entitlements scripts/hypervisor.entitlements target/release/cave-vmm-spike
target/release/cave-vmm-spike --kernel target/spike/Image \
  --initrd target/spike/initramfs.cpio.gz --stop-at "shell ready" </dev/null
```

| Measure | Result |
|---|---|
| VM set up (memory, GIC, kernel, device tree, vCPU) | 1.7 to 4.3 ms |
| First console output | 2.0 to 4.9 ms |
| Shell ready, inside the process (10 runs) | 42.0 to 55.3 ms |
| Shell ready, wall clock including exec (20 runs) | min 37.4, median 38.5, p90 40.0 ms, one outlier at 99.4 ms |
| Peak resident memory of the VMM process | 40 MB |

The first run after a rebuild is the slowest; page cache warm-up is the likely
cause (not measured separately).

## Findings

- With an in-framework GIC, Hypervisor.framework handles the guest's WFI
  inside `hv_vcpu_run` (seen in a `sample` of the process: the vCPU thread
  waits in `VcpuStateManager::wait_for_interrupt`). The VMM never gets a WFI
  exit, so a device thread must kick the vCPU with `hv_vcpus_exit` when it
  has work. P2.6 does this for console input.
- The virtual timer drives the guest tick (`arch_timer` on interrupt 27,
  about 200 interrupts a second at `HZ=250` while idle at the prompt).
- The PL011 receive interrupt (SPI 1, interrupt 33) works through
  `hv_gic_set_spi`.
- Input sent before the guest's UART driver starts is dropped, as on real
  hardware: the driver drains the receive FIFO when it probes.
