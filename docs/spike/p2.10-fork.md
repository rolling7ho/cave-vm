# P2.10: fork experiment

One memory snapshot is restored into two VMs in separate processes at the
same time. Each maps the snapshot's `memory` file copy-on-write
(`MAP_PRIVATE`). Each fork writes its own name to `/tmp/who` (tmpfs, so in
guest RAM), sleeps, and reads it back. Each sees only its own value, and both
power off cleanly. The snapshot file is unchanged.

**Answer:** A3 holds. Copy-on-write file mappings work as guest RAM with
16 KiB pages, and a fork is far under a second.

## Machine

Apple M4 Pro, 24 GiB, macOS 27.0.1 (26A434), using only APIs available on
macOS 26. Snapshot from P2.9: the P2.7 guest at its shell prompt, 1 vCPU,
512 MiB (25 MiB on disk).

## Steps

```sh
# make the snapshot as in docs/spike/p2.9-snapshot.md, then:
scripts/spike/fork-check.sh /tmp/snap
```

## Numbers

| Measure | Result |
|---|---|
| Two forks at once: independent state | WORKS (alpha saw alpha, beta saw beta) |
| Each fork: VM restored and ready | 2.1 and 2.2 ms |
| Ten forks at once: all ran a command and printed its output | 33.8 ms wall clock |
| Resident memory per fork after one command | 11.3 to 12.0 MiB |
| `cp -c` (clonefile) of the snapshot directory | median 2.2 ms (1.9 to 2.7), including starting `cp` |
| Restore from the clonefile copy | 2.5 ms, works |

The resident figure counts clean pages of the snapshot file, which the page
cache shares between forks, so the unique memory per fork is lower. Phase 4
should measure it with `footprint` or `vmmap`.

## What it means for phase 4

- **Fork from a snapshot:** map the memory file `MAP_PRIVATE` in each new
  VMM process. This is what the experiment did. No copy is made.
- **A fork that needs its own file** (to be snapshotted again, or to outlive
  the parent): `clonefile` the snapshot. On APFS this takes about 2 ms for a
  512 MiB sparse file and shares blocks until written.
- Saving, not restoring, is the slow step: 156 ms to write the memory file in
  P2.9. Forking a running VM costs a snapshot first, so saving is what to make
  faster.
