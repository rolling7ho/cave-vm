# Changelog

All notable changes to cave-vm are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions will follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) once there is a release.

## [Unreleased]

### Fixed

- Claude Code on the Mac could read the credentials in `.env` with its Read tool, since only Bash was denied. `cave agent` and the `.claude/settings.json` that `cave init` writes now also deny `Read(./.env)`, which covers Grep too. `cave agent` passes the list as one `--disallowedTools=` argument, so a prompt after `--` is no longer taken as a tool name.
- About one restore or fork in 80 under load never reached the guest agent and fell back to a disk boot after 50 seconds. A snapshot taken while a vCPU was inside an interrupt handler restored with that handler's priority still active in the GIC CPU interface, and the guest's end of interrupt did not clear it, so the vCPU took no interrupt again, not even its timer. `Machine::pause` now lets the vCPUs run on briefly and pauses again until none is in a handler. 450 stress rounds that each snapshot right after heavy guest writes now pass without a hang.
- `cave ls` sizes count blocks shared through APFS clones once, in the first row that uses them, and leave out blocks a disk shares with its base image, as `docs/cli.md` says. Before, a snapshot counted the whole disk it was cloned from.
- `cave gc` failed with a lost connection while a VM was running: data the VM had written but not flushed has no place on the volume yet, and its negative offset overflowed. It is now skipped.
- A fork made from a snapshot sometimes never answered and fell back to a disk boot after 50 seconds. The daemon cloned the snapshot's memory file before the VMM's last writes to it reached the disk, and an APFS clone takes only what is on disk. The daemon now flushes each file before it clones it.
- A restore drives every interrupt line to match its device before the guest runs. A vCPU that acknowledged an interrupt could pause for the snapshot before lowering the line, so the line was restored high with nothing pending.
- After a restore, `cave-vmm` tries the guest agent again after 100 ms rather than 2 s when a connection gets no answer, doubling the wait each time. The first connection is sometimes lost to the guest's vsock reset, which made a restore or fork take 2 s longer.
- `cave-vmm` keeps each agent connection it hands to the daemon open until the daemon's next request. Closing it right after sending it lost connections on macOS under load: the daemon got a connection that ended at the first reply.
- The guest agent removes a failed file write's temporary file before it replies, so a client never finds it after getting the error. CI caught the race as a flaky test.
- Interrupts that virtio devices raise from their own threads now wake an idle guest at once. Before, they waited for the guest's next timer tick, which delayed vsock connection setup by about 200 ms and network replies by up to a second.
- Restored spike snapshots got no more timer interrupts once the guest went idle, so they hung at 100% CPU. `hv_gic_state_get_data` leaves out each redistributor's SGI and PPI state; snapshots now save it per vCPU (format version 3, so older spike snapshots are refused).
- Device MMIO loads now honor sign extension (`LDRSB`, `LDRSH`, `LDRSW`) and 32-bit destination registers.
- A virtqueue buffer whose address range would wrap past the top of the address space is an error instead of an overflow, and an oversized `QueueNum` leaves the queue invalid instead of truncating to a valid size.
- A restored spike VM saved again now records the time of the second save, not of the restore, for its timers.

### Added

- The daemon keeps an audit log for each VM, `audit.log` in `.cave/` or in a fork's folder: every exec call with its arguments, credential names and exit code, and every file written through the daemon with its path and size, one JSON object per line. An exec is recorded even when the client goes away before it ends (P5.4).
- The audit log records the guest's network connection attempts, allowed or denied with the reason, such as `LAN`. `cave-vmm` keeps them until the daemon takes them with the new `take_connects` control request, every second and before a stop, and no longer writes them to `vmm.log` (P5.4).
- `cave inspect [--fork <name>] [--log] [--json]`: the policy, whether the VM is running and since when, its CPUs, memory and disk use, and the last 20 audit-log entries, or all of them with `--log`. It works on a VM that is not running too, reading the policy from `cave.toml` without fetching anything. The daemon's `inspect` reply gains `state` and `started_unix` (P5.5).
- The agent skill, `skill/cave/SKILL.md`: the rules for working inside the project's VM, the commands, and the setup steps the bootstrap skill on the website gives. `cave init`, and the setup `run`, `shell` and `exec` do on first use, write it to `.claude/skills/cave/SKILL.md`, replacing an older copy (P5.6).
- `docs/bootstrap.md`, the text of the bootstrap page on the website: what the agent will do with the pasted skill, the promise that it shows each command first and fetches nothing further, and the copy block, which a test keeps identical to `skill/cave/SKILL.md` (P6.6).
- Remote editing: `cave init` makes an SSH key and a host entry, `<folder>.cave`, in the data directory, and adds an `Include` line for the entries to the top of `~/.ssh/config`. VS Code Remote-SSH and Zed connect through `cave ssh-proxy`, which starts the VM, adds the key in the VM the first time and carries the connection over vsock with the daemon's new `ssh` request (P5.9).
- The daemon's `sync` module decides synced mode's file moves from SHA-256 hashes on the Mac, in the VM and at the last sync. A pull applies files changed only on the Mac, leaves files changed only in the VM, and stops on files changed on both sides. A sync writes files changed only in the VM and never writes over a Mac edit. `node_modules`, `target`, `.git`, `.cave`, the top-level `.env` and the paths in the root `.gitignore` are excluded, following git's pattern rules (P5.10, first part).
- `cave sync` and `cave pull` for synced mode. A sync writes the VM's changes to the Mac mirror through temporary files and lists Mac edits waiting for a pull and files changed on both sides; it waits for a VM that is not running. A pull takes a snapshot, then copies Mac edits into the VM, or applies nothing and lists the files changed on both sides. The state of the last sync is kept in `.cave/sync.json`, and `cave snapshot` and `cave agent` sync on their own (P5.10). The daemon's new replies are `synced` and `pulled`.
- The first-boot copy (D13): on a project VM's first boot, the daemon copies the project folder's files, except `.cave/` and the top-level `.env`, into `/workspace` once, as a tar stream through the agent, and `cave` says what that means for the Mac files. A copy that fails is tried again on the next start (P5.12).
- `docs/safety.md`: the threat model, the limits of the agent boundary (an agent with a host shell can step outside the VM, and Claude Code on the Mac keeps its non-Bash tools), what credential injection does not cover, and that the Mac mirror backs up source only (P5.11).
- A gate 5 end-to-end test, run with `CAVE_E2E_CLAUDE=1`: after `cave init`, Claude Code writes a file and runs a command with a credential through `cave mcp` only, with host Bash denied. The test checks that the reply shows `[API_KEY]` instead of the value, that `cave inspect --log` shows the policy, the write and the credential's name, and that the audit log never holds the value. It then checks that the snapshot before the run undoes it.
- `cave doctor`: checks for Apple Silicon, Hypervisor.framework, macOS 26 or later, the hypervisor entitlement on `cave-vmm`, 5 GB of free space and the daemon, each failure with its fix, exiting 1 if any fail. The daemon answers `doctor` by hashing every cached image and kernel against its digest. It changes nothing (P6.2).
- The image update detector: when a VM starts in a project with `[updates] check = true`, the daemon reads the image manifest in the background at most once a day and records the newest version of each image, and `cave doctor` says when a downloaded image has a newer one. It never updates anything, and with `check = false` it sends nothing (P6.7).
- The memory warning: after a VM boots, `memory is getting tight: N VMs are running and M GB is free` when macOS reports memory pressure or less memory is available than the VM's cap. VMs still boot; there is no cap on how many run (P6.1).
- First-run setup: before it starts the daemon, `cave` signs `cave-vmm` ad hoc with the hypervisor entitlement when it lacks it, and on the first run checks the chip, Hypervisor.framework and the macOS version first, stopping with the fix if one fails. The first `start` shows the progress of the kernel and image download (P6.3).
- The Python SDK, `sdks/python` (`cave_vm`): `Sandbox.open`, `exec` with stdin, environment and credentials, `read_file`, `write_file`, `snapshot`, `restore`, `fork` and `destroy`. It uses only the standard library and starts the daemon when needed. Its tests run against a fake daemon, and an e2e test drives a real VM through it (P6.4).
- The TypeScript SDK, `sdks/typescript` (package `cave-vm`): the same calls as the Python SDK, as `readFile`, `writeFile`, `forkNamed` and so on, with hand-written types. It uses only Node's built-in modules and needs Node 20 or later. Its tests run against a fake daemon, and an e2e test drives a real VM through it (P6.4).
- `cave agent claude [--in-vm] [--fork <name>] [-- <args>]`: boots the VM, prints the policy and takes a snapshot, then starts Claude Code on the Mac with `cave mcp` as its MCP server and the Bash tool denied, and prints how to undo the run when it exits. `--in-vm` installs Claude Code inside the VM with its installer on first use and runs it there on a pseudo-terminal. `cave mcp --fork <name>` makes the tools act on a fork by default (P5.8).
- `cave init` also writes the skill into `AGENTS.md` between marker comments, keeping the rest of the file, and sets up Claude Code: `.mcp.json` registers `cave mcp`, and `.claude/settings.json` denies the `Bash` tool, keeping the settings already there. Claude Code asks once to approve the `cave` server (P5.7).
- Credentials: an `exec` that names credentials, such as `API_KEY`, gets their values from the project's `.env` as environment variables, on the agent link only. Output that prints a value has it replaced with `[API_KEY]`, even split across two writes, best effort. The audit log records names only. A snapshot records the names injected since the VM's memory began, and the `restored` and `forked` replies carry them, so `cave restore`, `cave fork` and `cave export` warn. The MCP `exec` tool takes `credentials`, and the Rust SDK has `Command::credential` (P5.3).
- `ttl` in `cave.toml` now takes effect: once a VM has lived that long since its first boot, the daemon stops it and removes it as `cave rm --yes` would, checking every 10 seconds. A VM whose TTL ran out while the daemon was not running is removed when it is next started. The first boot is recorded in `booted` in the VM's folder (P5.5, D21).
- The Rust SDK, `cave-vm-sdk`: `Sandbox::open(".")` finds the project the way `cave` does, and `exec`, `run` (with a working directory, environment and stdin), `snapshot`, `restore`, `fork`, `fork_from` and `destroy` each send one request to the daemon, starting it when it is not running. Errors keep the daemon's code and say how to fix the problem (P5.1).
- `Sandbox::read_file` and `Sandbox::write_file` in the Rust SDK. Relative paths are under `/workspace`, a write creates missing folders, and both check the data's SHA-256 as `cave cp` does (P5.2).
- `cave mcp`, the MCP server on stdio, written by hand (decision 0013): `exec`, `read_file`, `write_file`, `snapshot`, `restore`, `fork` and `destroy` for the project in the current folder, with a `fork` argument to act on a fork. `destroy` removes forks only. `Sandbox::fork_named` in the Rust SDK addresses an existing fork (P5.2).
- The guest agent drops the guest's clean page cache once, 3 seconds after it starts, when boot has settled. Booting leaves over 100 MB of cached files the VM rarely reads again, and free page reporting now hands that memory back: a booted VM idles at about 192 MB instead of 285 MB. The gate 4 benchmark measures idle memory 8 seconds after the last command, and the booted memory target is 200 MB (P4.12d, decision 0012). Rebuild a local image with `image/debian/build.sh` to get the new agent.
- A virtio-balloon device for free page reporting: the guest reports memory it frees, and `cave-vmm` hands the host pages back to macOS (`GuestMemory::discard_mapped`, which unmaps the range from the hypervisor, gives the pages back with `MADV_FREE_REUSABLE` and maps it again; the hypervisor's mapping keeps pages in use otherwise). Freeing 500 MB in the guest brings the VM from 765 MB back to about 290 MB. The guest kernel enables `CONFIG_VIRTIO_BALLOON` and `CONFIG_PAGE_REPORTING` and reports blocks of 128 KiB; rebuild a local image with `image/kernel/build.sh`. Snapshots from before keep restoring without the device. Booted memory right after boot is unchanged, since the guest holds that memory (P4.12c).
- A snapshot of a running VM writes only the memory pages changed since the VM's last snapshot, or since it booted, on top of an APFS clone of that snapshot's memory: 32 ms instead of 595 ms for the benchmark VM, and the undo point every restore saves shrinks the same way. `cave-vmm` write-protects guest RAM in the hypervisor and records each page's first write; device writes are recorded as they happen. The snapshot format is unchanged (P4.12a, decision 0011).
- `cave restore` takes 81 ms instead of 247 ms and `cave fork --from` 130 ms instead of 154 ms, until a command runs. The daemon starts the new VMM process while it saves the undo point and stops the old VM, checks for the old VMM's exit every millisecond rather than every 20, and reads the host's OS build once. A restored vsock device holds packets for the guest until the guest has handled the transport reset, for at most 250 ms, so the first agent connection is no longer lost to the reset and retried. Files are flushed before a clone with `fsync`, which is enough for an APFS clone, rather than a full flush to the drive (P4.12b).
- `scripts/bench/gate4.py`, the gate 4 benchmark: boot, snapshot, restore, fork and ten-fork times and idle memory, end to end through `cave` with the real image, compared with the targets in decision 0005. The first results are in `docs/bench/gate4.md`. Ten forks meet their target; snapshot, restore, fork and memory miss theirs (P4.11).
- `cave export [snapshot] [-o <dir>]`: copies `/workspace` out of the VM, or out of a snapshot through a temporary fork, into a folder on the Mac, `.git` included, and says how many files and bytes it copied. An ignored end-to-end test exports a real VM and a snapshot and checks the files (P4.10).
- `cave gc [--yes] [--json]`: disk usage for the image cache and each project's disk, snapshots and forks, with blocks that APFS clones share counted once, and what is safe to delete (unused images, automatic snapshots beyond `keep`, unfinished snapshot folders), deleted after asking. Sizes come from each file's physical extents (`host::physical_extents` in `cave-vm-vmm`, through `F_LOG2PHYS_EXT`). The daemon now records each cached image's name for it (P4.9).
- `[snapshots]` in `cave.toml` now applies: `auto = false` stops `cave restore` from saving the state before it, and only the newest `keep` automatic snapshots are kept, the oldest deleted after each new one. Snapshots taken by name and the one being restored are never deleted (P4.8).
- Every running VM is suspended, all at once, when the Mac is about to sleep, through IOKit's system power notifications (`host::on_system_sleep` in `cave-vm-vmm`). A suspension outlives a reboot, and the next command resumes it. A test confirms the daemon can register for the notifications (assumption A10); whether a suspend fits in the time macOS allows before sleeping is checked by hand with `pmset sleepnow` (P4.7c).
- A VM unused for its `idle_suspend` time (30 minutes by default) is suspended, as `cave stop` would. It is in use while a command, shell, file copy or forwarded connection is open, and `cave run` counts as use. The daemon checks every 10 seconds; tests drive it with a fake clock (P4.7b).
- `cave stop` suspends the VM (D20): the daemon saves it, memory and all, to `.cave/suspended/` and stops it, `cave ls` shows it as suspended, and the next start resumes it with its processes and deletes the suspension. A start that turns the network off or on boots from the disk instead. A VM that cannot be saved keeps running. Snapshots and forks of a suspended VM take its memory (P4.7a).
- A gate 3 end-to-end test (`crates/cli/tests/e2e.rs`, `#[ignore]`d) runs the real `cave`, daemon and VMM against a locally built image: init, run and the image pin, exec and exit codes, every denied LAN range and the Mac refused at once, `cave shell`, a forwarded port, `cave cp` both ways, recovery from a killed VMM, and `cave rm`. It uses no network.
- `cave fork [name] [--from <snapshot>]`. An ignored end-to-end test forks a real VM both ways and checks that parent and forks run on their own, each with the process from before, and prints how long a fork takes (P4.6b).
- The daemon's `fork` request: a fork of a project's VM in `.cave/forks/<name>`, named `fork-1`, `fork-2` and so on by default, made from a fresh snapshot of the VM or from a named snapshot through APFS clones, and started from that memory. Requests with `fork` set act on it, `list` shows forks whether or not the daemon has run them, and `remove` with a fork's name stops and deletes it. Removing the project's VM stops its forks first (P4.6a).
- `cave snapshot [name]` and `cave restore [name]`. A restore that could not load the memory state warns and says the VM booted from the disk; one that did says how to undo it. An ignored end-to-end test snapshots a real VM, restores it with a process from before still running and the clock set, undoes the restore, and falls back to the disk when the memory file is damaged (P4.5b).
- The daemon's `snapshot` and `restore` requests. A snapshot of a running VM saves its memory through the VMM and leaves it running; a stopped VM's snapshot is a clone of its disk. Default names follow the design, `[ProjectFolder]-[YYYY-MM-DD]-[Distro]` with `-2` and on for collisions, and characters a name cannot hold become `-`. A restore first saves the current state as an automatic snapshot, then boots from the snapshot's disk and memory, or from its disk alone when the memory cannot be loaded, and says why. Snapshots are listed by `list` and removed by `remove` with their name (P4.5a).
- A restored VM's TCP connections through the network stack are reset instead of hanging. The snapshot `state` (now format version 5) lists the guest's open connections, and the restored stack makes the guest reset each one. An ignored hardware test, run only when `CAVE_E2E_TCP_TARGET` names a server, holds a connection open across a snapshot and restore and sees the reset and a new connection (P4.4).
- `cave-vmm` snapshots a running VM on the control link's new `snapshot` request (after the agent flushes the guest's file systems) and restores one from a `boot` that names a snapshot folder, with guest memory mapped copy-on-write. Each snapshot file is written under a temporary name and renamed, so a VM running from a snapshot can be snapshotted over it. An ignored hardware test boots the Debian image, starts a process, snapshots, restores in a new VMM and finds the process running and the clock set (P4.3c).
- `Machine::pause` and `Machine::resume` in `cave-vm-vmm`: every vCPU stops between exits, including powered-off ones, and saves its own state on its own thread with one host time taken once all have stopped, so the guest never sees its clock go back. The net and vsock devices stop writing guest memory from their own threads meanwhile, so memory and queue positions agree in a snapshot of a running VM (P4.3b).
- A restored vsock device sends the guest a transport reset (`VIRTIO_VSOCK_EVENT_TRANSPORT_RESET`) as soon as it has an event buffer, so the guest resets connections that were open to the old VMM instead of waiting on them. The agent's listening socket is not affected. Devices get a `restored` hook for this (P4.3a).
- Snapshots save every device: the virtio-mmio transport registers and, for block, net and vsock, the queues with the device's position in each, so a restored device carries on from the same ring slots. Frames waiting for the guest and host vsock connections are not saved; P4.3 and P4.4 handle what the guest sees. The VMM `state` format is now version 4. Checked on the Mac by snapshotting a Debian boot in the middle of disk I/O, with 1 and 2 vCPUs, and restoring it to the end of boot (P4.2).
- The versioned snapshot format in `cave-vm-daemon` (`docs/snapshots.md`): a `snapshot.json` manifest with the format version, VM settings, image, macOS build and the names of injected credentials, written atomically. A newer format is refused with a fix, and memory state from another macOS build falls back to a disk boot (P4.1).
- `cave images [--json]`: the base images from the manifest, with each one's digest, whether it is downloaded, how many projects use it and which one `base` stands for. An older version still downloaded or in use is listed with the newer digest. The daemon remembers each project it has run in its own data directory, so the count survives a daemon restart (P3.11f).
- `cave rm [name] [--yes]`: removes the project's VM, deleting `.cave/` and the daemon's state for it while `cave.toml` stays. It asks first, showing the size and, for a sealed project, that code only in the VM is lost; without a terminal it needs `--yes`. A `.cave` that is a symbolic link is removed without being followed (P3.11d).
- `cave shell`: an interactive shell in the VM as the `cave` user, booting it first if needed, on a pseudo-terminal that follows window resizes, with Ctrl-C going to the VM and the shell's exit code. Without a terminal it says to use `cave exec` (P3.11c).
- `cave cp <src>... <dest>`: copies files and folders between the Mac and the VM, with `:` marking the VM side as in `scp`. Files go through the agent's `file_read` and `file_write`, checked by SHA-256 on both ends and keeping their permission bits; folders go through `tar` on both sides, without macOS metadata. The daemon relays `file_read` and `file_write` to the agent (P3.11e).
- `cave exec -- <cmd>`: runs one command in the VM, booting it first if needed, with stdin passed through, stdout and stderr kept separate, and the command's exit code (128 plus the signal number when a signal ended it, 125 when cave itself fails) (P3.11b).
- `cave`: the command line's first commands, `init`, `run` (prints the startup policy and echoes widening flags), `stop` and `ls`, with project discovery, errors that say how to fix the problem, and a daemon client that starts the daemon on first use (P3.11a).
- Port forwarding to the Mac (`cave run -p 3000`, `-p 8080:80`): the daemon listens on localhost only and opens an agent `port_forward` connection per accepted connection. A Mac port in use is reported before the VM boots, with a fix; `-p` on a running VM adds a forward without a restart; stopping the VM closes the ports (P3.8).
- `cave-vm-daemon` serves `exec` and `shell`: each request goes to the guest agent over a new agent connection, and input, signals, terminal data, output and the exit status are relayed both ways. If the client goes away, the agent connection closes and the agent kills the program. Requests naming credentials are refused until P5.3 (P3.10c).
- `cave-vm-daemon`: connections to a running VM's guest agent, received from its VMM as file descriptors over the control link (`Vms::agent_connection`, D26). Asking for one on a stopped VM says to start it with `cave run`.
- `cave-vm-daemon` starts each VMM under a macOS sandbox profile (`crates/daemon/src/vmm.sb`, run with `sandbox-exec`): it can read and write only its project's `.cave/`, read the image cache and the kernel, read the Mac's DNS settings, and make outbound connections, with Hypervisor.framework still working. This confirms assumption A8 on macOS 26 (P3.13).
- `cave-vm-daemon`: the daemon socket (`daemon.sock`, user-only) with the hello handshake, one VMM process per VM with `start`, `stop` and `list`, crash detection so the next `start` relaunches a crashed VMM, and startup cleanup of VMM processes an earlier daemon left behind. The VMM control link and its messages (`cave-vm-proto::vmm`) are specified in `docs/protocol.md` (P3.10a).
- `cave-vm-daemon` reads `cave.toml` with every key and default from `docs/config.md`, refuses unknown keys and bad values with the line and a fix, and writes the image pin into the file without changing its comments or layout (P3.10b, D27). Adds `toml_edit`.
- `cave-vm-proto`: the daemon API requests and replies, with the reply objects written down in `docs/protocol.md` (P3.1b).
- `cave-vm-proto`: the length-prefixed JSON frame codec, the `hello` version handshake, `error` messages and every guest agent message from `docs/protocol.md` (P3.1).
- `cave-vm-agent`: the guest agent's exec with streamed output, stdin and signals, checked file reads and atomic file writes, port forwarding to guest loopback, and the control connection for ping, snapshot preparation and clock sync after restore (P3.6a).
- Userspace network stack in `cave-vm-vmm` (`nat`), built on smoltcp: the guest gets a fixed address on 192.168.127.0/24, the gateway answers ARP and ping, and frames with another hardware or IP address are dropped (P3.7b).
- Project disks in `cave-vm-vmm`: a 20 GB sparse `.cave/disk.img` created as an APFS clone of the base image, growable but never shrunk, with no absolute paths stored (P3.4). A `host` module wraps `clonefile` and `statfs` (D24).
- `cave run` boots a real project VM: the daemon reads `cave.toml`, fetches the image and its kernel into the cache, pins `image = "base"` to its digest on first run, and creates `.cave/disk.img` as a clone of the image, growing it when `[storage] disk` grows. A pinned project starts without reading the manifest. Forks and `-p` are refused until they land. The daemon binary is now named `cave-daemon`, the name the CLI starts (P3.12c).
- The image manifest (D28) in `cave-vm-daemon`: `images.json` is read from the latest GitHub release or from `CAVE_IMAGE_DIR`, a name resolves to its newest version and a pin to its own version and kernel, and the files it lists download into the image cache through `/usr/bin/curl`, HTTPS only. `image/manifest.sh` writes one for a local build (P3.12b).
- Image names and digests (`debian@sha256:...`) and the shared image cache in `cave-vm-daemon`: downloads are hashed as they are written and kept only when size and SHA-256 match, so an interrupted or wrong download leaves nothing behind (P3.12a).
- virtio-net device in `cave-vm-vmm`: frames from the guest go to a backend trait, and frames for the guest are delivered from any thread with a bounded backlog. No offloads; the link is always up (P3.7a).
- virtio-vsock device in `cave-vm-vmm` with no socket files (D26): the VMM opens connections to guest ports as Unix socket pairs, and guest connections to the host go to a handler per port, with credit-based flow control and per-connection threads so a slow peer never blocks a vCPU (P3.5).
- Decision 0010 (D28): base images and the kernel come from an `images.json` manifest on each GitHub release, and `CAVE_IMAGE_DIR` points at a local build.
- Decision 0008 (D26): vsock connections without socket files, after socket paths in `.cave/` hit macOS's 104-byte limit.
- The guest kernel and the Debian base image (P3.9): `image/kernel/build.sh` builds a built-in-only 6.18 kernel with ext4, the `ip=` boot address, systemd's needs and Docker's (namespaces, cgroups v2, overlayfs, netfilter); `image/debian/build.sh` builds a raw ext4 Debian trixie image with git, node, npm, python, curl, vim and openssh-server, the agent started by systemd, a `cave` user with passwordless sudo, and `/workspace`. The file system grows to fill the 20 GB project disk at boot, and each VM gets its own machine ID and SSH host keys. Both build in an Apple container.
- The Ubuntu base image (P6.8): `image/ubuntu/build.sh` builds Ubuntu 26.04 LTS (resolute) for arm64 with the same packages and customization as the Debian image, and `image/manifest.sh` lists it when it is built. `cave init --image ubuntu` uses it. `UBUNTU_MIRROR` picks another ports mirror for the build.
- `cave-vm-agent`: the pty shell with resize and signals, the vsock listener on port 1024, and `image/agent/build.sh`, which builds the agent as a static aarch64 musl binary in an Apple container (P3.6b).
- `cave-vm-agent` runs commands and the shell as the `cave` user with its groups (such as `docker`) and login environment, not as root, as `docs/cli.md` specifies. New files and the folders made for them belong to `cave`, and replaced files keep their owner. `image/agent/test-as-root.sh` runs the tests as root in an Apple container so this is checked.
- Outbound TCP through host sockets in the userspace network stack, with the network policy: `nat` mode denies private, link-local and shared ranges, every mode denies loopback, multicast, reserved ranges and the Mac's own addresses, and `lan` mode allows private ranges. A denied or refused connection resets the guest's, and each attempt is recorded for the audit log (P3.7c, P3.7e).
- Outbound UDP and DNS in the userspace network stack: each flow gets a host socket, checked against the same policy and closed after 60 seconds idle, and DNS queries to the gateway go to the Mac's DNS servers from `/etc/resolv.conf` (P3.7d).
- `cave-vmm` networking: unless `net` is `off`, the VM gets a virtio-net device behind the userspace NAT stack, which now runs on its own thread and wakes for guest frames (`Stack::run`, `GuestFrames`). The policy denies the Mac's own addresses, and connection attempts are noted in `vmm.log` until the audit log takes them.
- `cave-vmm`: the per-VM process the daemon starts. It speaks the VMM control link on its standard input, boots the kernel with the project disk as `/dev/vda` and the vsock device, replies `booted` once the guest agent answers `ping` and has set the guest clock to the Mac's (the VM has no clock of its own), and hands out agent connections as file descriptors (D26). A guest that stops or panics while booting is reported at once, and the VM stops when the link closes. Networking is wired in next.
- virtio-blk device in `cave-vm-vmm` on a raw image file: read, write, flush, device ID, and discard, which punches holes in the image so freed blocks return to the Mac (P3.3). The spike takes `--disk <file>`, and its kernel config gains virtio-mmio, virtio-blk, virtio-net and vsock.

- Cargo workspace with an empty crate for each component, the Rust toolchain pinned to 1.99.0, and a `deny.toml`.
- CI that runs `cargo fmt`, `cargo clippy`, the tests, `cargo deny` and `cargo audit` on every pull request.
- `cave-vm-hvf`: a safe wrapper around Hypervisor.framework for VMs, guest memory mappings, vCPUs, registers, the virtual timer and the GICv3 interrupt controller, including saving and restoring its state.
- Guest memory in `cave-vm-vmm`: page-aligned regions from anonymous memory or a file mapped copy-on-write or shared, mapped into a VM through `cave-vm-hvf`.
- Spike kernel config and busybox initramfs in `image/spike/`, built in an Apple container, that boot to a shell in about 40 ms (`docs/spike/p2.7-boot.md`).
- A backend trait in `cave-vm-vmm` with a mock backend for tests and a Hypervisor.framework backend.
- A direct kernel boot path: arm64 Image loading, a generated device tree, PSCI, a PL011 UART console and the virtual timer, with a `cave-vmm-spike` binary that boots a kernel on the terminal. Input wakes the vCPU (Hypervisor.framework handles guest WFI itself), and `--stop-at` stops the VM when the guest prints a given text, for boot timing.
- Spike snapshots: `cave-vmm-spike --snapshot` saves a paused guest (vCPU, GIC, timer, UART and sparse memory file) and `--restore` resumes it in a new process in about 3 ms (`docs/spike/p2.9-snapshot.md`).
- Fork experiment: `scripts/spike/fork-check.sh` restores one snapshot into two VMs at once with copy-on-write memory and checks they diverge (`docs/spike/p2.10-fork.md`).
- Spike report with baseline numbers and the approved gate 4 targets (`docs/decisions/0005-spike-report.md`).
- 2-vCPU spike numbers, measured with `scripts/spike/vcpu-bench.py`, as an addendum to the spike report. The gate 4 targets stand.
- Virtio-mmio transport (version 2) and split virtqueues in `cave-vm-vmm`, with indirect descriptors, level-triggered interrupts and 32 device slots in the device tree. Malformed queues from the guest are errors, never VMM crashes.
- Secondary vCPUs: PSCI `CPU_ON`, `CPU_OFF` and `AFFINITY_INFO`, each vCPU on its own thread, and `cave-vmm-spike --cpus <n>` to boot, snapshot and restore with more than one. Spike snapshots record each vCPU's power state.
